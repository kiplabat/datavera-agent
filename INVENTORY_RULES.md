# Local inventory rule — Datavera agent

1. Before researching, load the complete local inventory for this account (`username` in agent_config.json) and every company it publishes for (`companies`), including published, draft, review, rejected, suspended and archived records. Stop if the bootstrap is missing, incomplete or unreadable.
2. Do not ask the model to paginate the remote inventory in ordinary research runs. Use local inventory search and candidate checks. Do not paste the catalogue into the model context.
3. Before selecting a candidate, search the local inventory for its topic, source and alternative wording. Check the proposed title/source against the index. Treat related titles as review leads; absence of an exact match is not proof of semantic uniqueness.
4. Keep the imported snapshot immutable. Append confirmed new IDs and status observations to `inventory/events.jsonl`. Never delete old entries or rewrite the event history. Repeated observations of the same dataset ID update the derived view, not the number of unique datasets.
5. After successful remote draft creation, immediately append the confirmed dataset ID, title, owner and status. After successful submission, append the returned/confirmed status before declaring the local operation complete. A moderated submission is not automatically published.
6. Never append a proposed dataset as though the server accepted it. Failed or ambiguous mutations remain in operation journals and must be reconciled. Local recording failure after remote success is an incomplete operation, not permission to resubmit blindly.
7. Use `agent.py` (or `dv_publisher.py` for a hand-made payload) for mutations from this installation. Both write through `dv_publisher.py`, which journals every create/submit, uses the server's `client_request_id` idempotency key, and appends confirmed events. Browsing is read-only; Datavera is never browsed.
8. This cache tracks this account's company and personal records, not every other creator on the platform. Submissions made through other clients are unknown until an explicit deterministic `inventory_store.py sync` refresh. Research does not silently trigger a remote refresh.

Enforcement (v3): `agent.py` loads the full catalogue in Python before any stage and stops on a corrupt baseline/event file; the model never sees or pages the catalogue. Topics strongly matching existing titles are skipped; candidates whose source page, data-file URL, data-file content hash or similar title match a catalogue record are rejected; exact-title duplicates are blocked at draft time. `agent_state/ledger.jsonl` records every topic, page and data file tried so repeat runs move on. These are lexical/identity checks: they do not guarantee semantic uniqueness or analytical quality, and drafts deserve review. With automatic submission on (`stop_after_default: submit`), a run that raises a REVIEW warning stays a draft. Moderated accounts' submissions go to Datavera's review queue; accounts that publish directly go live.
